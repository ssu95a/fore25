# Сборка новых классов Fore25 отдельно от JInvFore Java 8

Новые классы `ru.inversion.fore` используют Java 25 и JavaFX 25. Их нельзя
компилировать с `source`/`target`/`release` 8 или запускать на Java 8.
Отдельный POM читает эти исходники из существующего `src/main/java`, но
компилирует только `ru/inversion/fore/**`. Старые исходники JInvFore и его
корпоративный parent в эту сборку не входят.

Все команды ниже выполняются из корня репозитория. Сначала проверьте JVM Maven:

```sh
mvn -version
```

В выводе должна быть Java 25. При другой версии выберите установленный JDK 25
в `JAVA_HOME` и в настройках Maven Runner в IDE. Одной замены `release` в POM
недостаточно: сам Maven должен работать на подходящем JDK.

## Контролы и действия

Для независимой проверки `IForeControl`, `ForeTextField`, кнопок, меню,
действий и FXML используется уже существующая сборка Scene Builder:

```sh
mvn -f scenebuilder/pom.xml -Pheadless clean test
```

Профиль `headless` добавляет Monocle только в тестовую JVM; он не входит
в JAR для Scene Builder. Тесты используют настоящие классы JavaFX 25.0.4
и ControlsFX 11.2.4. Без профиля тесты используют обычную графическую среду.
Этот набор не включает `FormControllerTest` и не проверяет весь runtime.
Эта UI-сборка не зависит от `JInvCommon` и не компилирует JInvFore Java 8.
В этот набор входят проверки `ActionKeyBinder`: оба сочетания CREATE,
disabled, конфликты, смена клавиш, области разных Scene и снятие привязок.

## Все новые классы и тесты формы

Контроллер, launcher, валидация, настройки приложения и адаптер данных используют классы
`Checks`, `TaskContext`, `IExceptionInfo`, `S` и `IDataSet` из `JInvCommon`. Отдельная
сборка подключает готовый JAR `ru.inversion:JInvCommon:1.0.0`, а не компилирует
старый JInvFore:

```sh
mvn -f standalone/pom.xml -Pheadless clean test
```

Этот запуск также проверяет настоящий запуск FXML-формы, veto закрытия,
снятие клавиш на FX-потоке и последующий `closeResources()` на виртуальном
потоке. Пример регистрации действия и описание lifecycle находятся
в [руководстве Scene Builder](../scenebuilder/README.md).

Текущий набор тестов форм и пример `TableView` не создают `TaskContext`;
инициализация корпоративного приложения и подключение к БД не требуются.
В примере редактору явно передаются `null` вместо контекста и окно владельца:
конструктор `FormLauncher` с родительским контроллером обращается к
`getTaskContext()` и создаёт его лениво. `JInvCommon` остаётся зависимостью
сборки, поэтому его JAR и зависимости должны быть доступны Maven.

Нужен доступ к корпоративному Maven-репозиторию через ваши рабочие Maven
настройки либо уже установленный в локальном Maven-репозитории `JInvCommon`
с его зависимостями. Версию можно переопределить через
`-Djinvcommon.version=<ваша-версия>`. Если Maven сообщает о недоступном
Nexus, `maven-default-http-blocker` или отсутствующем `JInvCommon`, это
отдельная ошибка разрешения зависимостей. Сборка `scenebuilder` выше
корпоративный репозиторий не использует.

JAR, скомпилированный под Java 8, можно использовать как зависимость сборки
на JDK 25; совместимость конкретного runtime проверяется тестами. Обратное
направление не работает: Java 8 не сможет загрузить новые классы Fore25.

## Если новые исходники пока внутри старого JInvFore

Оба каталога с POM можно использовать рядом с тем же `src` в рабочей копии
JInvFore. Запускайте их через `mvn -f ...` на JDK 25.
Чтобы отдельная старая сборка JInvFore продолжала работать на Java 8,
исключите новые пакеты из её `maven-compiler-plugin`:

```xml
<configuration>
   <excludes>
      <exclude>ru/inversion/fore/**</exclude>
   </excludes>
   <testExcludes>
      <testExclude>ru/inversion/fore/**</testExclude>
   </testExcludes>
</configuration>
```

Эти исключения относятся только к старому Java 8 POM. Старые классы также
не должны ссылаться на новые классы Fore25. Для IDE задайте отдельному
Fore25 Maven-проекту JDK 25, а JInvFore оставьте на JDK 8.

## Пример TableView и редактора записи

Импортируйте `standalone/pom.xml` как Maven-проект, выберите JDK 25 и запустите
из IDE основной класс `ru.inversion.fore.demo.table.TableViewDemo`.
В параметрах JVM укажите `--enable-native-access=ALL-UNNAMED`.
Нужен настоящий `JInvCommon` из описанной выше рабочей конфигурации Maven.

В примере используется `ForeTableView` с колонками ID и названия.
Пять стандартных действий разделяются между кнопками панели, меню и клавишами:

| Действие | Клавиши | Условие доступности |
|---|---|---|
| Создать | F2, F6 | Всегда |
| Изменить | F4 | Выбрана запись |
| Просмотр | F3 | Выбрана запись |
| Удалить | Shift+F6 | Выбрана запись |
| Обновить | F8 | Всегда |

Редактор открывается через `FormLauncher` в режиме `INSERT`, `EDIT` или `VIEW`.
Сохранение вызывает `ok()`, проверяет непустое название длиной до 120 символов
и возвращает черновик через `FormResult`. Отмена не меняет сохранённую запись.
Просмотр разрешает только чтение. `RecordStore` хранит записи в настоящем
`ArrayDataSet` из `JInvCommon`. `ForeDataSetAdapter` связывает его с таблицей:
сохранение и удаление вызывают методы набора, а таблица получает изменения
через события. При сортировке выбранная запись следует за курсором набора,
в том числе после замены записи новым экземпляром. После удаления курсор
выбирает соседнюю запись в порядке `IDataSet`; пустой список отключает действия
с выбранной записью. При закрытии снимаются привязки действий и адаптер данных.
Enter и двойной щелчок по строке используют то же действие изменения, что
кнопка и пункт меню. Сохранение выбора и выбор после удаления выполняет
`ForeDataSetAdapter`; создание черновика и работа с хранилищем остаются в контроллере.
API контрола описан в [руководстве Scene Builder](../scenebuilder/README.md#foretableview).

`RecordStore` хранит демонстрационные данные в памяти: после перезапуска снова
появляются три исходные записи. Это пример подключения формы; доступа к БД нет.
При переносе в приложение используйте свой `IDataSet` и операции сохранения.

Проверки создания, валидации, отмены, изменения, сортировки, просмотра и удаления
входят в тесты полной сборки:

```sh
mvn -f standalone/pom.xml -Pheadless clean test
```

## ForeDataSetAdapter

`ru.inversion.fore.dataset.ForeDataSetAdapter<T>` связывает любой `IDataSet<T>`
с обычным `TableView<T>` или с `ForeTableView<T>`. Создание и закрытие адаптера
выполняются на потоке JavaFX:

```java
adapter = ForeDataSetAdapter.bind(dataSet, table);
```

Адаптер получает начальные записи и текущий курсор, подписывается на события
строк, навигации и самого набора. `INSERT`, `UPDATE`, `DELETE`, `REFRESH`
и завершение `EXECUTE` публикуют актуальное состояние. Обычный `List` внутри
набора поддерживается без установки глобальной фабрики и без `BaseApp`.

Все записи хранятся только в `IDataSet`. Таблица получает доступную только
для чтения оболочку: `get(index)` обращается к `dataSet.getRows().get(index)`,
а `size()` — к `dataSet.getLoadedRowCount()`. Копии списка, снимков записей,
`SortedList` и отдельного массива индексов в адаптере нет. Привязка,
обновление и навигация не обходят все записи. Объём служебного состояния
адаптера не зависит от числа строк.

Индексы таблицы и набора совпадают. Выбор строки вызывает
`dataSet.setCurrentRowNum(index)`, а событие навигации выбирает этот же индекс
в таблице. Поэтому отдельные экземпляры равных POJO и повторные ссылки
на одну запись различаются без поиска по `equals()`.

Сортировка выполняется в слое данных. Штатная сортировка JavaFX отключается
при привязке, поскольку она материализует список строк. Для заголовков задайте
`table.setSortPolicy(...)`: обработчик должен упорядочить сам набор,
сохранить его текущую запись и вызвать `adapter.refresh()`. Пользовательская
политика, установленная до привязки, сохраняется. В демонстрации `RecordStore`
сортирует свой `ArrayDataSet`; для SQL используйте сортировку своего набора
и повторное выполнение запроса. Фабрики значений и оформления колонок
настраиваются штатным API JavaFX.

| API | Назначение |
|---|---|
| `bind(dataSet, table)` | Создать одну привязку к таблице |
| `getDataSet()`, `getTable()` | Получить участников привязки |
| `getCurrentRow()`, `currentRowProperty()` | Получить текущую запись, опубликованную на потоке JavaFX |
| `refresh()` | Опубликовать данные после изменений без событий |
| `close()`, `isClosed()` | Снять привязку и проверить её состояние |

События строк и `refresh()` заменяют только оболочку `table.items`,
сохраняя заголовки сортировки и восстанавливая выбор по курсору. Это нужно
для обычных списков `JInvCommon`: событие группового удаления не содержит
все прежние строки. Адаптер не хранит их для формирования `getRemoved()`.
Для уведомлений используйте `InvalidationListener` на `table.itemsProperty()`;
слушатели старой оболочки не получают событий `ListChangeListener`.
Привязка количества строк также должна зависеть от свойства таблицы:

```java
countLabel.textProperty().bind(Bindings.createIntegerBinding(
        () -> table.getItems().size(), table.itemsProperty()).asString());
```

Для отображения поля текущей записи можно использовать обычную привязку JavaFX:

```java
nameLabel.textProperty().bind(Bindings.createStringBinding(() -> {
   var row = adapter.getCurrentRow();
   return row == null ? "" : row.name();
}, adapter.currentRowProperty()));
```

Свойство инвалидируется и при `REFRESH` того же экземпляра POJO. Очистка
выделения таблицы сохраняет курсор непустого набора: существующий контракт
`JInvCommon` не поддерживает сброс курсора через `setCurrentRowNum(-1)`.
Для доступности действий по выделению используйте модель выбора таблицы.

Чтение таблицей и изменение `IDataSet` следует согласовывать: оболочка видит
данные сразу и не обеспечивает изоляцию потоков. Перенос уведомлений на
поток JavaFX не делает исходный список потокобезопасным. События рабочего
потока объединяются в одно отложенное уведомление без очереди записей
и снимков. При его обработке читается актуальное состояние набора;
после закрытия уведомления игнорируются. Выполнение запросов и выбор
рабочего потока остаются у владельца набора. Пример в памяти изменяет
данные на потоке JavaFX.

В `closeGuiResources()` сначала снимите привязки полей формы, затем закройте
адаптер. Он удаляет все свои подписки и восстанавливает прежний список таблицы.
Если штатная политика сортировки была отключена адаптером и не заменена
владельцем, она также восстанавливается. Замена `table.items` автоматически
снимает адаптер, сохраняя новый список. Событие `CLOSE` набора также снимает
привязку. Сам набор остаётся у владельца; закрывайте адаптер до освобождения
набора, поскольку `ArrayDataSet.close()` не формирует событие `CLOSE`.

Для изменения связанного набора используйте `IDataSet.insertRow()`,
`updateCurrentRow()`, `removeCurrentRow()` и `clear()`. Методы
`ForeTableView.replaceItems()` предназначены для таблиц с изменяемым
`ObservableList`. Ключи для ручной замены списка в этой привязке не требуются:
выделение определяется курсором `IDataSet`.

Тесты адаптера используют реальные `ArrayDataSet` и `ReaderDataSet` из
`JInvCommon`, включая подкачку страниц, события рабочего потока и закрытие.
Проверка на 200 000 записей запрещает копирование списка и полный обход
при привязке, обновлении, вставке, удалении и навигации.
`TaskContext` и подключение к БД для них не нужны. Адаптер и демонстрация входят
в сборку `standalone`; независимая сборка Scene Builder сохраняет только GUI классы.
